Working principles

  • Keep invariants inside the smallest practical transactional boundary.
  • Treat timeouts as uncertain outcomes until resolved.
  • Model compensation as new business work, with its own failure path.
  • Separate authoritative state from caches, search indexes, and projections.
  • Evaluate guarantees per operation and failure mode.

Before the patterns: decide what must stay true

Home · Next: distributed transactions

An invariant is a business rule that must remain true across successful operations.

In the loan acceptance example, our sample loan workflow: “An accepted reservation must not make available lending capacity negative.” A dashboard being five seconds late is a different kind of problem.

Term Plain meaning Loan example
Transaction A unit that commits or aborts within a supported boundary Save a reservation and decrement capacity together
Atomicity All writes in that unit commit, or none do No reservation without its capacity deduction
ACID consistency Transactions preserve declared rules and constraints Available capacity stays nonnegative
Isolation Rules controlling what concurrent transactions can observe Two applicants compete for the last capacity
Durability Acknowledged committed data survives the failures the storage system promises to handle A restart does not forget the reservation
Linearizability Each operation appears to take effect at one instant between call and response, respecting real-time order A later capacity read sees the completed reservation
Eventual consistency Replicas converge if updates stop and propagation succeeds Search eventually shows an accepted loan

ACID's C and CAP's C mean different things. Also, “ACID” does not mean every database transaction runs at serializable isolation. PostgreSQL isolation

The concurrency mistake

Two requests each read available capacity = 100. Each wants 80. A separate read followed by an unconditional write can accept both.

An illustrative SQL reservation inside a transaction:

UPDATE LendingPools
SET Available = Available - @Amount
WHERE TenantId = @TenantId AND Id = @PoolId
  AND @Amount > 0 AND Available >= @Amount;
-- Require exactly one affected row; otherwise reject the reservation.
-- Insert the reservation and its outbox event in this SAME transaction.
-- Add UNIQUE(TenantId, ReservationId) for retry protection.

The conditional write protects this row's rule. A rule spanning multiple rows may need a different constraint, locking strategy, or serializable transaction. A retry must not deduct capacity twice.

Command, event, and row change

Message Means Can be rejected?
ReserveCapacity Please do this business action Yes: insufficient capacity
CapacityReserved This business fact already happened Consumers may fail to handle it; the fact still happened
UPDATE LendingPools captured by CDC This stored representation changed Does not by itself explain the business intent

Start with fewer boundaries

One deployable .NET app can contain Loan, Capacity, and Agreement modules. If the rules fit one transactional database, keep a local transaction. Extract a service for a concrete ownership, scaling, isolation, or release need; service extraction adds failure boundaries.

Design sequence: state the invariant, owner, consistency requirement, and failure behavior before naming a product.

1 · Distributed transactions

Home · Next: event sourcing

One business action crosses more than one transactional resource. Who decides whether it succeeds?

Accepting a loan offer updates Loan's database and Capacity's database. A normal transaction in one database cannot roll back a separately committed write in the other.

Partial failure

  1. Capacity reserves 500,000 units and commits.
  2. Agreement creation fails.
  3. The reservation is still committed. Returning HTTP 500 does not release it.

The architecture needs a recovery rule, not just an exception handler.

Choice Guarantee / behavior Best fit here Cost
One local transaction Atomic writes inside the database's supported boundary Loan and capacity can share ownership Shared boundary; scaling and ownership constraints
Two-phase commit (2PC) Coordinated atomic commit across enlisted resources Short operations, compatible resources, managed transaction coordinator Prepared resources can hold locks while a decision is unavailable
Saga Local commits plus explicit recovery over time Independent services and long business workflows Intermediate states, compensation and recovery logic

2PC is a real option in systems that support it. It is not universally obsolete, and arbitrary HTTP APIs cannot simply be enlisted. PostgreSQL prepared transactions

How 2PC actually works

Phase 1 — prepare: a coordinator asks each participant whether it can commit. A “yes” participant durably prepares; it has promised to obey the final decision.

Phase 2 — decide: the coordinator durably records a commit decision once every participant is prepared, then communicates it. If a participant votes no, the transaction aborts. Recovery redelivers the recorded outcome when needed.

Crash case: a prepared participant that cannot discover the durable decision cannot safely guess “abort after ten seconds.” Another participant might already have committed. This uncertainty explains classic 2PC blocking.

Atomic commitment is not the same as global serializability or linearizability. Isolation and replication protocols determine additional guarantees. 2PC and consensus solve different coordination problems, although real databases may combine them.

Protocol boundary: two phases are protocol rounds, not “write one database, then write another.”

.NET and enterprise implementation

For one relational database, EF Core normally wraps one SaveChanges call in a transaction when the provider supports transactions. An explicit transaction can group multiple operations. It does not make an HTTP call transactional. Provider, operating system, and deployment support matter for System.Transactions and distributed transactions. EF Core transactions

A separate Capacity service is justified only when its ownership or operational requirements warrant the boundary. If it does, use a durable reservation API with an operation ID and a saga. Expose Pending, Active, and ManualReview states instead of claiming immediate all-or-nothing success.

NoSQL is not synonymous with no ACID. DynamoDB supports transactional operations within documented boundaries. That does not create a transaction spanning DynamoDB, SQL Server, and an external lender. DynamoDB transactions

Operational questions: Who owns the coordinator? Where is its decision stored? How do prepared transactions recover? How long can locks remain? What is the failure recovery procedure?

Design position

The first choice is the smallest transactional boundary that can enforce the invariant. Supported enlisted resources can use 2PC for atomic commitment, with blocking and recovery costs. Independent services usually need a saga, explicit intermediate states, idempotent operations, and reconciliation rather than a global rollback.

Boundary: A timeout does not establish failure: the transaction may have committed before its response was lost.

2 · Event sourcing

Home · Next: CDC

Store the business facts that changed an entity. Derive its current state from those facts.

Ordinary CRUD might store Loan.Status = Active. An event-sourced loan retains the accepted offer, reserved capacity, prepared agreement, and activation facts as its authoritative history.

Event stream example

Stream version Persisted fact State after applying it
1 OfferAccepted(OfferId, OfferVersion) Accepted
2 CapacityReserved(ReservationId) Capacity secured
3 AgreementPrepared(AgreementId) Ready to activate
4 LoanActivated(ActivatedAt) Active

The stream belongs to TenantId + LoanId. A projection builds a dashboard row from it. A snapshot at version 3 lets the command handler load that state and apply only version 4.

Snapshots accelerate loading; they do not replace the authoritative history. Microsoft event sourcing

Keep these ideas separate

Idea What makes it different
Event-driven architecture Services react to messages; their databases may still use CRUD
Event sourcing Domain events are the authoritative record for a selected entity
Audit log Supplementary history; the current row may remain authoritative
CQRS Separate write and read models; event sourcing is optional
CDC Capture storage changes; row changes may lack domain intent

CQRS reference · AWS event sourcing

Concurrent writes and replay

Expected version: two commands load version 3. The first appends version 4. The second must fail its append with expected version 3, reload, and re-evaluate its business rule. Do not silently append both. Enforce stream identity and version uniqueness atomically in the event store.

Replay: apply recorded facts to rebuild state or a projection. Replaying LoanActivated must not send another welcome email or transfer funds again. Isolate rebuild processors from live side-effect handlers. Historical decisions should use recorded inputs, not today's pricing API. Fowler: external interactions

Projection recovery: keep checkpoints; make updates duplicate-safe. If a delta depends on prior facts, process in stream order and detect gaps. Rebuild into a new projection, catch up, validate, then switch readers.

An event broker is not automatically a suitable event store. Required capabilities include durable history, per-stream reads, ordering, concurrency control, and a retention/recovery model that meets the business requirement.

Is it worth the operational cost?

Event sourcing is an optional alternative for the Loan lifecycle, not a requirement for the whole platform. Start with CRUD plus reliable events unless historical reconstruction has clear value.

Implementation considerations:

  • Version the OfferAccepted contract so an old offer remains interpretable after pricing rules change.
  • Keep personal details in a separately governed profile store; events reference identifiers.
  • Record correlation and causation IDs without treating them as authorization.
  • Test “given history, when command, then new facts,” plus schema compatibility and rebuilds.
  • Measure stream length, replay time, projection lag, and version-conflict rates.

Deleting or encrypting personal information in immutable history requires a retention design with the responsible privacy team; append-only storage is not automatic regulatory compliance.

When to avoid: ordinary profile CRUD, small reference tables, or teams that do not need historical reconstruction. Event sourcing adds work to schema evolution, debugging, recovery, and queries.

Design position

Domain facts are authoritative; current entity state and query projections are derived. Expected-version checks protect appends, while consumers handle duplicates and projection lag. Replay stays separate from external side effects. Adoption is selective and justified by historical reconstruction requirements.

Boundary: A current-state row plus LoanUpdated notifications is event-driven integration; it is not event sourcing.

3 · Change data capture (CDC)

Home · Next: sagas

Follow committed database changes so another system can update its own view.

the sample loan workflow still has a legacy loan database. Advisers need fast search without adding expensive text searches to the transaction database. CDC feeds an indexer; the database remains authoritative.

Change propagation

  1. A loan status update commits in the legacy database.
  2. The capture mechanism exposes the committed change and its position.
  3. An indexer applies it to a document keyed by tenant and loan ID.
  4. Search becomes current after capture and indexing delays.

SQL Server CDC exposes changes through change tables and query functions. It does not independently push a business event to every subscriber; a consumer or connector supplies the rest of the pipeline. SQL Server CDC

CDC is a mechanism; an outbox is a design

Capture this Consumer sees Main tradeoff
Business table Column-level changes Fast legacy integration, but coupled to table structure
Outbox table A deliberately defined event payload Application change required, but clearer integration contract

Debezium can capture an outbox table and route its payload into events. CDC and outbox can be used together. Debezium outbox router

Bootstrap, offsets, and recovery

An index needs existing rows as well as future changes. Use a connector's supported consistent snapshot-to-stream handoff, or explicitly design and test an equivalent algorithm. “Copy rows, then start listening” can miss writes in between.

Maintain a restart position, such as a database log position and connector offset. If a crash happens after indexing but before the checkpoint is saved, records can be replayed. Use idempotent upserts and handle deletes/tombstones.

Each search document stores its source version. A late version 5 must not overwrite version 6. Enforce this check in the target write; an application-side read-then-write check can race. Version namespaces must survive snapshots, rebuilds, and failover.

When a connector falls behind, retained logs can consume storage. If required changes expire, a restart offset alone cannot recover them: resnapshot or reconcile. Monitor source retention, replication-slot health, lag, and disk usage. Debezium PostgreSQL connector

AWS guarantees

DynamoDB Streams retains changes for up to 24 hours and orders modifications for an individual item. It is not a permanent event-history store or a global ordering guarantee. DynamoDB Streams

A stream record appearing once in the stream does not mean a Lambda handler runs once. Lambda stream processing is at least once; duplicates must be safe. Lambda with DynamoDB

Example integration policy:

  • Use search for discovery, then verify authoritative state before accepting a binding offer.
  • Treat deleted rows as explicit removals from search, including tenant-scoped identifiers.
  • Keep borrower documents and sensitive fields out of broad capture streams.
  • Roll out schema changes with consumer compatibility and monitoring.
  • Reconcile source and target counts/versions; a healthy process does not prove correct data.

CDC can reduce invasive changes to a legacy app, but connector privileges, source configuration, load, schema evolution, and recovery still require engineering work.

Design position

CDC moves committed storage changes into downstream views. The design includes a consistent bootstrap, restart positions, duplicate-safe target writes, deletes, schema evolution, and retention-gap recovery. An outbox provides a deliberate integration contract; search remains a derived view.

Boundary: A restart offset is useful only while the required source changes remain available.

4 · Sagas

Home · Next: coordination

A saga is a business workflow of local transactions, with a recovery plan for partial completion.

For this example, LoanActivated means the internal application is ready for settlement. It does not mean external money has moved. Keeping that boundary explicit makes recovery easier to reason about.

What happens if agreement preparation fails?

Step Committed work Recovery in this example
Reserve capacity Capacity held for this application Release this reservation
Prepare unsigned agreement Draft agreement exists Void this draft
Activate loan Application crosses our chosen business pivot Finish required downstream work or invoke an explicit servicing process
Send welcome Customer receives a message Retry if needed; a sent message cannot be unsent

A pivot is a business decision about a point of no return. It is not a special global database commit.

Compensation is new work

ReleaseReservation(R123) is a fresh transaction. It releases only R123; it does not restore the capacity table to an old snapshot and erase other customers' reservations.

A compensation can fail too. Save recovery progress, retry safe actions, and move unresolved cases into an owned manual-review queue. Compensating transaction

Five failure cases to design explicitly
Failure Recovery behavior
Duplicate reserve command Same reservation ID returns the existing result; do not deduct again
Agreement rejects input Stop forward progress and release capacity
Reserve call times out Query by operation ID or retry idempotently; outcome is unknown
Release fails Persist Compensating; retry or escalate; never pretend cancellation completed
Delayed success arrives after cancellation Apply state/version checks; release a late reservation or reconcile it

Isolation: local ACID transactions do not isolate the whole saga. Concurrent acceptance and cancellation need legal state transitions, concurrency checks, and ownership rules. A reservation may have an expiry and renewal policy; activation must verify it is still valid. Microsoft saga

Persist the saga ID, tenant ID, current state, completed step IDs, operation IDs, deadlines, retries, and compensation results. A correlation ID helps find the workflow; it does not deduplicate an operation.

.NET / AWS mapping

A durable .NET worker or a workflow engine can coordinate steps. A try/catch across HTTP calls in one process is insufficient: process termination can lose the recovery plan.

AWS Step Functions Standard is one candidate for this long-lived flow. Define explicit failure routes and compensation tasks; the service does not invent business compensation for you. AWS saga orchestration

Workflow execution guarantees do not automatically make an external action exactly once. Explicit retries, duplicated start requests, and a lost provider response still need analysis. Standard, asynchronous Express, and synchronous Express have different execution semantics. Workflow types

Before real settlement, add a provider-supported idempotency key and a status/reconciliation API. Never issue a second transfer merely because the first call timed out. Whether reversal is legally and operationally possible is a separate business contract.

Track the age of pending sagas, compensation failures, reservation expiry, and manual-review backlog. A completed HTTP request is not proof the business workflow completed.

Design position

A saga coordinates local commits and recovery across a business workflow. Agreement failure releases the specific capacity reservation. Progress is durable, steps and compensations are idempotent, and uncertain outcomes are reconciled. Global isolation is absent; unresolved recovery remains visible in a pending or manual-review state.

Boundary: Deleting an email record cannot undo delivery to the customer.

5 · Choreography vs orchestration

Home · Next: CAP

The distinction is who owns the “what happens next?” decision.

Choreography: services react to facts

Capacity handles OfferAccepted, then emits CapacityReserved. Agreements handles that fact. If agreement preparation fails, its failure fact triggers reservation release through a defined subscriber. No central workflow component owns the whole sequence, but the sequence still exists.

Orchestration: a workflow makes the decisions

The workflow sends commands and handles results. Participants own their data and business rules; the coordinator owns sequence and recovery decisions. An orchestrator may use asynchronous messages—it need not hold open an HTTP request.

Compare Choreography Orchestration
Next-step logic Distributed across subscribers Visible in a workflow
Adding an independent subscriber Usually straightforward May not need a workflow change if subscribing to published facts
Multi-step timeout and recovery Cross-service contracts must coordinate Workflow can own deadlines and progress
Coupling Event schema and implicit sequence Command/result contracts and coordinator
Failure investigation Reconstruct the event path Inspect workflow history, then participant traces

Both require durable messaging, idempotency, schema evolution, and operational ownership. AWS choreography

A practical hybrid

An orchestrated activation workflow is appropriate when capacity expiry, agreement failure, and cancellation require one understandable recovery policy. Publish LoanActivated for independent analytics and notification subscribers.

Why a hybrid? Analytics should not need to become a mandatory activation step. A reporting outage should not block a valid activation. If notification is legally required before activation, that is a different business rule and belongs in the coordinated flow.

Commands express an intention directed to an owner. Events express a fact that may interest several subscribers. Do not name a command LoanActivated when the receiver can still reject activation.

A coordinator is a logical central decision point, not necessarily one unreplicated process. Replicate and persist its workflow state. Participants must still handle duplicate commands and retain independent authorization checks.

Coordination tradeoffs

“Is choreography loosely coupled?” It removes direct knowledge of subscribers, but required event sequences and contracts still couple business behavior. A cycle can repeatedly trigger work.

“Does orchestration make a distributed monolith?” Not inherently. It becomes problematic when the coordinator owns every participant's business logic or all services must change together. Keep decision boundaries deliberate.

“Does a saga require orchestration?” No. A saga can use either style. An event chain without compensation or recovery semantics is not automatically a well-designed saga.

“What if the orchestrator fails?” Recover durable workflow state; redeliver outstanding commands safely. Do not reconstruct progress from volatile memory. In Step Functions, evaluate the execution model and explicit retries. AWS orchestration

Design position

Required steps with shared deadlines and compensation favor orchestration. Independent reactions favor choreography. Both rely on durable state, versioned contracts, and duplicate-safe participants. The coordinator owns sequence and recovery; each participant retains its domain rules.

Boundary: A broker can carry orchestrated commands; broker usage alone does not determine the coordination style.

6 · CAP theorem

Home · Next: distributed cache

When replicas cannot communicate, a system cannot guarantee both linearizable operations and successful responses to every request at every non-failing node.

The partition is the condition that exposes the conflict. A “CA” label does not remove the possibility of partitions.

Use the numbers

Both sides last knew available lending capacity was 100. The network splits. One client asks each side to reserve 80.

  • If both sides independently accept, accepted reservations total 160. Without preallocated rights, the invariant is broken.
  • If only the side with authoritative ownership/quorum may accept, the isolated side rejects or defers. It preserves the chosen correctness rule but sacrifices availability for that operation.

This is an illustrative application of CAP, not a proof that all banking systems have one fixed CAP label. Gilbert & Lynch, Perspectives on the CAP Theorem

Translate the letters accurately

Term Interview meaning Avoid this shortcut
C — consistency Linearizable behavior, equivalent to one real-time-respecting copy for the modeled operations “Every replica is always physically identical”
A — availability Every request at a non-failing node eventually gets a successful response permitted by the modeled service “99.99% uptime” or returning an error
P — partition Communication can be lost or indefinitely delayed between parts of the system “A database table partition”

A rejection may be correct behavior, but it does not satisfy CAP availability for the requested operation. The theorem's availability is not a bounded-latency SLO.

Choose by operation, not by product slogan

Example partition policy:

Operation Partition behavior we choose Business reason
Reserve capacity Accept only with authoritative ownership; otherwise defer/reject No over-allocation
Browse indicative products Serve a labeled cached view if policy allows Staleness is acceptable for discovery
Display activation status Show last known status plus freshness; confirm before action A stale view must not cause duplicate activation
Edit a draft note Consider offline capture with an explicit conflict policy A merge may be acceptable

A queued request marked Pending is not a successful reservation. Asynchronous acceptance changes the API contract; it does not evade CAP.

Advanced alternative: preallocate independent reservation rights to regions. Each can accept only within its own rights during isolation. That can preserve the invariant for bounded operations, but sacrifices flexibility and requires safe rights transfer. It is a different coordination design, not unlimited availability.

CAP does not answer every consistency question

Atomicity asks whether a set of writes commits together. Isolation asks how concurrent transactions interact. Linearizability asks whether operations respect real-time order. Eventual consistency describes convergence. The required property needs to be stated explicitly.

Outside partitions, latency and coordination still matter. PACELC is a useful additional lens: during a partition, consider availability versus consistency; otherwise, consider latency versus consistency. It is not a replacement for a concrete workload and database guarantee. Abadi: PACELC

Do not assign all Redis deployments the same consistency label. Redis Cluster documents asynchronous replication and possible loss of acknowledged writes under failures. A shared cache is not automatically an authoritative financial store; the deployment guarantee matters. Redis Cluster specification

A partition policy records the failure, affected operation, chosen outcome, and client recovery behavior. A CP/AP abbreviation alone does not capture these decisions.

Design position

Partition behavior is defined per operation. Capacity reservation requires authoritative coordination; affected requests defer when coordination is unavailable. Product browsing can tolerate a labeled stale view. Queued acceptance changes the API contract but does not complete the underlying reservation.

Boundary: A 503 response from an isolated replica does not satisfy CAP availability for the requested operation.

7 · Distributed cache

Home · Next: connected enterprise scenario

Several app instances share a cache so repeated reads can avoid expensive authoritative work.

“Distributed” does not necessarily mean a full copy beside every server. The cache may be an external shared service with shards and replicas; the network hop still exists.

Cache-aside flow

  1. The API checks tenant:T1:products:v3.
  2. On a hit, return the cached indicative product list.
  3. On a miss, read the authoritative catalog, cache the result with an expiry, and return it.
  4. On a catalog update, commit the database change, then invalidate or update the cache according to policy.

Cache-aside does not guarantee the cache always matches the database. Cache-aside pattern

Cache policy by data type

Data Example policy Why
Indicative product list Cache briefly; show freshness where useful Some staleness acceptable
Binding offer Use a versioned authoritative offer and validate acceptance Wrong terms have business consequences
Available lending capacity Cached value may inform a display; authoritative conditional write decides Stale reads cannot allocate scarce capacity
Permissions / tenant access Enforce current authorization policy; cache only with deliberate revocation rules A key naming convention is not access control
The invalidation race

Even “write database, then delete cache” has a race:

Time Reader Writer
1 Cache miss; reads old product version 5
2 Pauses before filling cache Commits version 6
3 Deletes cached product key
4 Writes version 5 into the empty cache

For indicative data, choose a bounded absolute TTL and document the tolerated stale interval. TTL bounds the life of that stale entry after fill; it is not a strong-consistency guarantee. Sliding expiry alone can keep a frequently accessed stale value alive.

For stricter reads, bypass the cache or design a coordinated version/fencing strategy. Merely checking a cached version outside the target write is another race. A reliable invalidation event helps recover from lost invalidation, but does not automatically solve every concurrent stale fill.

Common failure patterns
Problem Symptom Possible response
Stampede Many misses load the same expensive data Coalesce loads; assess coordination across instances
Synchronized expiry Many keys expire together Add bounded TTL jitter
Hot key One product dominates traffic Measure load; consider a small L1 cache with explicit staleness
Penetration Repeated requests for missing records Brief negative caching where safe; validation and rate limits
Cache outage Every API falls back to the database Short cache deadlines, bounded fallback concurrency, load shedding
Wrong tenant key One tenant's data appears in another's response Trusted tenant scoping plus authorization on every path

Fail open or closed? An indicative catalog may fall back to the database. A security decision may need to reject when freshness cannot be established. Base the decision on the data's contract.

Write-through updates the cache through a write path. Write-behind defers storage writes and requires a loss/recovery design. Cache-aside lets the app coordinate cache and storage. Names alone do not define atomicity.

ASP.NET Core's IDistributedCache abstracts cache access. It does not provide a database transaction, a cross-instance lock, or automatic correctness. Redis is one provider. ASP.NET Core distributed caching

Measure hit ratio alongside p95/p99 latency, cache timeouts, evictions, stale-age samples, database fallback load, and key cardinality. A high hit ratio with wrong data is failure.

Design position

Cache-aside suits indicative catalog reads with tenant-scoped keys, absolute expiry, and invalidation after committed changes. The design accounts for stale fills, stampedes, and database load during cache failure. Binding offer acceptance validates authoritative versioned data.

Boundary: A shared remote cache retains a network hop; its benefit comes from avoiding more expensive authoritative work.

Combined example · loan acceptance

Home · Reliability companions

The goal: accept a valid offer without over-reserving capacity, and recover if later work fails.

The example combines offer acceptance, capacity reservation, agreement preparation, and activation across separate data owners.

Requirements before products

Requirement Design implication
No negative lending capacity Atomic conditional reservation in the owning store
Same acceptance retry creates one workflow Tenant-scoped idempotency record and stable operation ID
Agreement failure must release capacity Saga compensation with durable progress
Dashboard may lag up to 5 seconds under normal operation Async projection with measured lag and a freshness indicator
Binding terms must be the accepted version Store and validate immutable offer ID/version and validity
Adviser belongs to one or more authorized tenants Server-derived tenant context and per-operation authorization
No invisible stuck work Deadlines, reconciliation, alerts, and an assigned operations owner

These requirements define the example; they are not measured production guarantees.

Acceptance flow

  1. API receives AcceptOffer. Validate authenticated tenant, permissions, offer version/expiry, and request key. Atomically save acceptance, idempotency result, and outbox event. Return 202 Accepted with an operation/status URL; this means queued work, not an active loan.
  2. Outbox relay publishes the accepted fact. Retry safely if publication is uncertain. A duplicate event must map to the same durable workflow, not a second reservation.
  3. Workflow reserves capacity. Capacity owns its invariant and reservation ID. Commit reservation, conditional decrement, and resulting event locally.
  4. Workflow prepares the unsigned agreement. On definitive failure, release the reservation and record cancellation. On a timeout, resolve the agreement operation's outcome before assuming failure.
  5. Workflow activates. Confirm the reservation and agreement remain valid. Persist the legal state transition with concurrency protection. Reject or reconcile racing cancellation.
  6. Independent consumers react. Update dashboard/search; send allowed notifications. Failed analytics does not undo an otherwise valid activation.

The base design uses current-state tables plus an outbox. Optional event-sourced variant: replace the Loan write model with an authoritative event stream only if reconstruction is required. Publish from a durable mechanism tied to the event append; do not add an unprotected second write.

Capacity planning and operations

Hypothetical load: 100,000 acceptance attempts/day is about 1.16/second on average. A 100× burst is about 116/second. If each attempt creates five messages, the burst is approximately 580 messages/second before retries. Reads, document processing, hot tenants, and retry storms need separate estimates.

Use measurements to set budgets. Example targets to validate: status reads p95 under 200 ms, normal projection lag under 5 s, and an alert when pending activations exceed their agreed workflow deadline. Do not hide long business workflows behind a short HTTP latency SLO.

Tenant isolation: tenant ID comes from trusted authentication/authorization context. Scope database keys, unique constraints, message validation, and caches. RLS can add defense in depth but requires deliberate session/context management. A message field from another service is not enough to authorize a cross-tenant action.

Recovery: test backup restoration, workflow-state recovery, replay without external side effects, and reconciliation of active reservations against workflow state. An outbox cannot recover data already lost outside the storage durability model.

Security: use least-privilege service identities, protected transport/storage, restricted borrower-document access, and redacted telemetry. Preserve only the business evidence required by the agreed retention policy.

Architectural position

A modular monolith is sufficient when the invariant fits one database. Independent service boundaries introduce a need for durable orchestration, local invariant enforcement, and reliable event delivery. Search and indicative catalogs may lag; reservation and offer validation use authoritative state.

The supporting patterns that make the seven useful

Home · Design questions

A saga needs reliable steps. Reliable steps need durable intent and safe retries.

1 · Transactional outbox: do not lose the intent

Save the business change and its event record in one local database transaction. A separate relay publishes committed records. If the process dies after commit, the event record remains available to the relay.

If the relay publishes and dies before marking a record sent, it may publish again. The outbox closes the database/broker dual-write gap; it does not guarantee exactly-once delivery. AWS outbox

Illustrative EF Core sketch — not a complete runnable application:

// Both entities use the same DbContext and transactional database.
loan.Accept(offerVersion);
db.OutboxMessages.Add(new OutboxMessage(eventId, tenantId, loan.Id,
    loan.Version, "OfferAccepted", payload));
await db.SaveChangesAsync(ct); // One local commit with a supported provider.
// A durable relay publishes later; do not publish directly as a second write.

The actual API also needs a unique request key and an atomically stored idempotency result. Outbox schema should carry a stable event ID, tenant, aggregate identity/version, type/schema version, payload, and creation time. Relay retry/lease state depends on polling vs CDC.

2 · Inbox and idempotency: do not repeat the effect

An inbox records which events a specific handler has processed. In the same transaction, claim the message ID and apply its local mutation. A unique constraint arbitrates concurrent delivery.

Conceptual transaction algorithm:

BEGIN
  INSERT ProcessedMessages(TenantId, ConsumerName, EventId)
  -- Unique conflict: abort this attempt and treat as already processed.
  APPLY local business change
  INSERT outgoing event if needed
COMMIT
ACK incoming message only after commit

Writing the marker before an external effect can lose the effect; writing it afterward can duplicate the effect. For external calls, use a durable outgoing intent, a stable provider idempotency key, and reconciliation of unknown outcomes. Idempotent APIs

Design request keys around business intent: (TenantId, Operation, ClientKey). Keep a payload fingerprint; reject the same key with different inputs. Define retention relative to the full retry/redrive window. Expiring a dedup record can make an old retry new work.

3 · Ordering and concurrency: deduplication is not sequence control

AgreementPrepared v3 arriving before CapacityReserved v2 can break a delta-based projection even when neither is a duplicate. Partition related events by aggregate, track sequence/checkpoints, and handle gaps according to the contract. A timestamp alone is not a global ordering protocol.

A complete-state projection may safely ignore older versions with an atomic conditional write. An event that increments a balance cannot simply discard missing predecessors. For concurrent database commands, use conditional writes or optimistic concurrency and re-evaluate rules after conflicts. EF Core concurrency

4 · Timeouts, retries, dead letters

Tool Use Avoid
Timeout Bound waiting and resource consumption Interpreting timeout as proof of failure
Backoff + jitter Spread retry load Every client retrying at once
Retry budget Bound attempts and end-to-end duration Multiplying retries at every service layer
Circuit breaker Temporarily stop calls to a repeatedly failing dependency Assuming it repairs that dependency
Bulkhead / concurrency limit Keep one slow dependency from exhausting the app Unlimited fallback to the database
Dead-letter queue Isolate repeatedly failing messages for investigation Treating it as successful completion

Retry transient failures when the operation is safe to retry. Business rejection normally needs a new decision, not the same request repeated forever. AWS backoff and jitter

For SQS, receiving a message is not deletion. Visibility timeout temporarily hides it; handlers can still see duplicates. A crash after commit but before delete is why local effects need idempotency. SQS visibility · At-least-once delivery

A dead-letter procedure needs an alarm, owner, diagnosis, fix, and controlled redrive. Reuse the original business identity; generating a new ID can bypass deduplication. SQS DLQs

5 · Observe the business outcome

Log TenantId, LoanId, SagaId, OperationId, EventId, and a trace ID where permitted. Keep sensitive payloads out of logs. Count duplicate suppression and out-of-order events; measure outbox age, consumer lag, compensation failures, and unresolved operations. A trace is a diagnostic aid, not the durable workflow state.

Design questions

Home

Concise answers to common design decisions and failure cases.

Distributed transactions

Related notes

1. Why not put both HTTP calls inside a database transaction?

The remote service is not automatically enlisted. The local transaction cannot undo a separately committed remote operation.

2. What if a 2PC coordinator fails after prepare?

Prepared participants may be unable to decide safely until the durable outcome can be recovered. Locks and resources can remain held.

3. Does 2PC provide linearizability?

Atomic commitment alone does not establish that guarantee. Ask about isolation, real-time ordering, replication, and the complete protocol.

4. When would you avoid a saga?

When the invariant fits a single local transaction, or the business cannot tolerate intermediate outcomes and has no acceptable recovery contract. Revisit the boundary first.

5. Does NoSQL rule out transactions?

No. For example, DynamoDB supports transactions within specified limits. Verify the specific product and scope rather than infer from a category label.

Event sourcing

Related notes

6. Is publishing LoanUpdated event sourcing?

Only if persisted domain facts are the authoritative record used to derive state. CRUD plus emitted events is usually event-driven integration.

7. How are conflicting appends prevented?

Atomically compare an expected stream version during append. On conflict, reload and re-evaluate the business rule.

8. Can live consumers be reused during a rebuild?

Only after separating replay from external effects. Rebuild projections without sending emails, repeating provider requests, or using current external inputs for past decisions.

9. What do snapshots optimize, and can the stream be deleted?

They reduce the work needed to rehydrate long-lived entities. Deleting authoritative history changes reconstruction capabilities and requires an explicit retention design.

10. Does event sourcing require CQRS?

No. They address different concerns and are often combined. Likewise, CQRS can use ordinary current-state tables.

11. How do old events survive a schema change?

Use compatible evolution, explicit schema versions, and tested upcasting where appropriate. Preserve original meaning and validate rebuilds before switching readers.

CDC

Related notes

12. How are existing records loaded into a new index?

Use a consistent snapshot with a tested handoff to the change stream. A naive copy-then-subscribe process can miss concurrent writes.

13. Why can a CDC consumer see duplicates?

The sink update may finish before its checkpoint is durable, so recovery can replay changes. Make the target write safe to repeat.

14. Is CDC the same as an outbox?

No. CDC captures stored changes. An outbox stores intentional integration messages with the business transaction; CDC can relay that table.

15. What if the connector is down beyond retention?

Determine whether the required log positions still exist. If not, resnapshot or reconcile; retrying an unavailable offset does not recover the gap.

16. A DynamoDB record appears once in its stream; is processing exactly once?

No. Lambda may process that stream record more than once. Stream storage and consumer effects have different guarantee boundaries.

Sagas

Related notes

17. Is compensation a rollback?

No. It is a new business action that counteracts an effect, possibly after other work has observed it. It may not restore the exact original state.

18. What happens if compensation fails?

Persist recovery progress, retry safe actions, and escalate unresolved cases with an accountable owner. Do not report successful cancellation while capacity remains reserved.

19. The provider timed out. Should I compensate immediately?

First resolve the unknown outcome using a stable operation ID, status query, or safe retry. The provider may have already completed the work.

20. How do two concurrent sagas avoid overspending capacity?

The capacity owner atomically enforces the invariant; workflow messages alone do not. Reservations, legal transitions, and concurrency checks also matter.

21. What is a pivot?

A business-defined boundary after which the workflow normally completes forward rather than automatically undoing earlier work. Its location depends on what is irreversible.

22. How is late success handled after cancellation?

Validate current workflow state and operation identity. Run the defined late-success compensation or reconciliation path instead of reviving a cancelled flow blindly.

Coordination

Related notes

23. Does choreography remove coupling?

It removes direct control of subscribers but retains event-contract and business-sequence coupling. Map the full flow, including failures and cycles.

24. Must orchestration be synchronous?

No. The coordinator can send durable asynchronous commands and wait for correlated results while persisting progress.

25. Can one system use both styles?

Yes. Orchestrate required activation steps and publish final facts for independent reporting or notification reactions.

26. Is the orchestrator always a single point of failure?

It is a logical control point. A durable replicated implementation can recover; a single process with only in-memory state cannot.

CAP

Related notes

27. Why is pick any two misleading?

The consistency/availability conflict is exposed during a partition. In a networked system you must define partition behavior, not assume partitions can be removed by a label.

28. Does returning 503 satisfy CAP availability?

No. A returned error does not fulfill the successful read/write operation required by the modeled service.

29. Is CAP consistency the C in ACID?

No. CAP uses linearizable behavior; ACID consistency is about preserving validity constraints through transactions.

30. Is the entire loan platform CP or AP?

That is too coarse. Explain guarantees and partition behavior per operation, such as authoritative reservation versus stale-tolerant browsing.

31. Does queuing every write solve CAP?

Queue acceptance is not a completed reservation. You have changed the user-visible contract and still need to resolve the actual coordinated operation.

Distributed caching

Related notes

32. Can write-then-invalidate still return stale data?

Yes. A reader can fetch an old value before the write and fill the cache after invalidation. Use the documented stale-data policy or a stronger coordinated design.

33. How are cache stampedes controlled?

Coalesce concurrent loads and bound database fallback. A per-process lock only coalesces that process; several instances may still load the same key.

34. What happens when the cache is down?

Use a short cache deadline and a workload-specific fallback policy. Protect the authoritative database with bounded concurrency or load shedding.

35. Should lending capacity be cached?

It can be displayed as an estimate, but the reservation decision must use the authoritative invariant-enforcing operation.

36. What belongs in a tenant cache key?

A trusted tenant identity plus resource and any representation-specific scope/version. Authorization still needs enforcement; a key prefix is not a security boundary.

Cross-cutting decisions

Related notes

37. A worker commits, then crashes before acknowledgment. What now?

The message can return. An inbox marker and its local mutation must have committed atomically so redelivery produces no extra effect.

38. The outbox relay publishes, then crashes before marking sent. Is the design broken?

Duplicate publication is expected in that crash window. Stable message identity and duplicate-safe consumers handle it; the outbox prevents lost durable intent.

39. How is silently stuck work detected?

Measure workflow age, reservation expiry, outbox age, projection lag, and manual-review backlog. Reconcile business records; process health alone is insufficient.

40. What belongs in an architectural decision?

Record the invariant, authority, viable boundary, failure behavior, recovery, tradeoffs, and validation under load and faults.
